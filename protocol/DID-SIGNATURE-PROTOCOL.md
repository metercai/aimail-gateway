# DID-Signature Protocol (aimail profile) — normative

| Item | Value |
|---|---|
| Status | Normative for `aimail` / `aimail-gateway` / `did-sdk` |
| Version | `v=1` |
| Byte vectors | [`vectors/did-signature.json`](vectors/did-signature.json) (generated by `protocol/vectors/gen_did_vectors.py`) |
| Design rationale | `aimail` repo: `docs/did-vc-email-authenticity-plan.md` |

This document is the **single source of truth** for the bytes on the wire. The companion plan document
explains *why*; this one explains *what*, exactly.

Any change to a field layout, an ordering rule or a digest choice MUST update this file, re-run
`protocol/vectors/gen_did_vectors.py`, and bump the `v=` value if the change is not backward compatible.

---

## 1. Scope

Two headers:

| Header | Produced by | Trusted? |
|---|---|---|
| `DID-Signature` | the **sending client** (holds the `did:key` private key) | No — it is a *claim*, forwarded unchanged |
| `DID-Auth-Results` | the **receiving MTA** | Yes — downstream trusts only this |

Plus three on-chain anchor payload definitions (`EmailBinding`, `DomainControl`, and the rules that keep
`IssuedVc` out of scope for this profile).

Non-goals: this profile does not replace SPF/DKIM/DMARC, does not implement `did:web`/`did:peer` for the
signer, and does not cover `Bcc` (an SMTP-level limit).

## 2. Constants

| Name | Value |
|---|---|
| `HEADER_NAME` | `DID-Signature` |
| `RESULTS_HEADER_NAME` | `DID-Auth-Results` |
| `SYSTEM_MAIL_HEADER` | `X-AIMail-System` |
| `PROTOCOL_VERSION` | `1` |
| `SIGNING_TAG` | `DID-Signature-v1` |
| `CONTENT_TAG` | `Content-v1` |
| `EMAIL_BINDING_TAG` | `EmailBinding-v1` |
| `BODY_HASH_PREFIX` | `sha256:` |
| `ANCHOR_HASH_PREFIX` | `blake2b:` |
| `ANCHOR_REF_PREFIX` | `chain:` |
| `ATTACHMENT_SEPARATOR` | `TAB` (`0x09`) |

**Two primitives, split by layer** (do not mix them):

| Layer | Primitive | Used by |
|---|---|---|
| Inside the message | **SHA-256** | `bh`, `rh`, `name_hash`, `file_hash` |
| On chain | **BLAKE2b-256** | `AnchorRecord.payload_hash` (e.g. `EmailBinding`) |

`BLAKE2b-256` means BLAKE2b with a **32-byte digest parameter** (`Blake2b<U32>`). It is *not*
`BLAKE2b-512` truncated and *not* `BLAKE2s-256`.

## 3. Data flow

```text
sender SDK ── Content-v1 ──┐
   (holds did:key)         ├── sign ──> DID-Signature ──> /send ──> gateway
                           │                                          │
                    rh ────┘                                    forwards unchanged
                                                                       │
                                                              MTA receives, verifies,
                                                              injects DID-Auth-Results
                                                                       │
                                                    payload.did ──> recipient agent SDK
                                                                       │
                                                              re-verifies independently
```

The sending service provider MUST NOT sign, re-sign, strip or rewrite `DID-Signature`, and MUST NOT alter
the signed body.

---

## 4. Signed object

### 4.1 `Content-v1` projection

UTF-8, every line terminated by `\n` **including the last one**:

```text
Content-v1
{subject}
sha256:<body_hash>
{attachment_count}
1<TAB>sha256:<name_hash><TAB>sha256:<file_hash>
...
```

* `{subject}` — subject with trailing whitespace removed (`rstrip` of spaces and tabs). No other change.
* `{attachment_count}` — decimal, no padding, `0` when there are no attachments.
* Attachment lines are emitted **in submission order**, numbered from `1`, contiguous.
* Each field is hashed **separately before** entering the projection; never concatenated raw.

### 4.2 Body canonicalization

Applied to the body **before** hashing. Only three operations, none of them MIME-related:

1. normalize line endings: `\r\n` → `\n`, then lone `\r` → `\n`;
2. strip trailing spaces and tabs from **every** line;
3. drop trailing empty lines.

Join with `\n` and append exactly one trailing `\n`. An empty body hashes as the empty string (no newline).

Interior blank lines and interior whitespace are preserved — a receiver must reproduce them byte for byte.

**The body already includes the agent signature trailer** (`"\n\n-- \n" + agent_signature`). Order is fixed:
trailer appended by the client **first**, then hashed. The sending provider no longer appends it.

### 4.3 `rh` (recipient hash)

Over the recipients the client submitted as `To ∪ Cc`:

1. normalize each address: strip, drop a trailing `(comment)`, extract the addr-spec from `Name <addr>`,
   strip again, lowercase;
2. drop empty results;
3. sort lexicographically (byte order);
4. join with `\n` (no trailing newline; empty set ⇒ empty string);
5. SHA-256, prefixed `sha256:`.

`Bcc` is not covered — an SMTP architectural limit, not a promise this profile makes.

### 4.4 Signing input

Seven lines, **every one terminated by `\n` including the last**:

```text
DID-Signature-v1
{did}
{from}
{t}
{vc}
{bh}
{rh}
```

* `{did}` — `did:key:z…`, exactly as it appears in the header;
* `{from}` — the bare `From` addr-spec, lowercased, no display name;
* `{t}` — decimal Unix seconds, no padding;
* `{vc}` — `chain:<anchor_id>`, exactly as in the header;
* `{bh}` — `sha256:` + hex of the `Content-v1` projection (§4.1);
* `{rh}` — `sha256:` + hex of §4.3.

No field may contain `\n` or `\r`. Signature is Ed25519 over these bytes (`s` in the header).

## 5. `DID-Signature` header

### 5.1 Fields

| Field | Required | Meaning |
|---|---|---|
| `v` | yes | protocol version, `1` |
| `did` | yes | must start with `did:key:`; other methods are `did_unsupported` |
| `t` | yes | Unix seconds; accepted window `now-300 .. now+5` |
| `s` | yes | base64url **without padding** of the 64-byte Ed25519 signature |
| `vc` | yes | `chain:<anchor_id>`, the anchored `EmailBinding` record |
| `bh` | yes | echo of the signed `bh` |
| `rh` | yes | echo of the signed `rh` |

`bh`/`rh` are echoed because the verifier necessarily recomputes them: without the claimed values a
tampered body is indistinguishable from a broken signature. **The signature remains authoritative**;
the echoes only classify a failure and can never turn a failure into a pass.

### 5.2 Wire form

```text
DID-Signature: v=1; did="did:key:z6Mk…"; t=1765144656; s=<base64url>;
  vc="chain:<anchor_id>"; bh="sha256:<64hex>"; rh="sha256:<64hex>"
```

Field order when emitting: `v, did, t, s, vc, bh, rh`. Quoted strings support `\"` and `\\` escapes.

### 5.3 Parser rules (normative)

1. **Unfold first**: replace `CRLF` (or `LF`) followed by one or more spaces/tabs with a single space.
2. Reject the header if the **unfolded** form exceeds `998` octets.
3. Reject duplicate parameter names.
4. Ignore unknown parameters (forward compatibility).
5. Reject an unterminated quoted string.
6. `t` must parse as a positive integer.

A real header measures **353 octets** unfolded (5 folded lines at 78 columns) — the same order of
magnitude as `DKIM-Signature` (300–600).

## 6. `DID-Auth-Results` header

```text
DID-Auth-Results: result=verified; integrity=pass; address=verified; did-id="did:key:z6Mk…"
DID-Auth-Results: result=failed; integrity=fail; address=unknown; reason=body_hash_mismatch
```

| Field | Values |
|---|---|
| `result` | `verified` / `failed` / **`unknown`** |
| `integrity` | `pass` / `fail` / **`delegated`** |
| `address` | `verified` / `failed` / `unknown` |
| `did-id` | present only when `address=verified` |
| `reason` | present only when `result=failed` |

Emission order: `result, integrity, address, did-id, reason`.

`result=verified` **iff** `integrity=pass` **and** `address=verified`. When `integrity=fail` the verifier
MUST skip the anchor query and emit `address=unknown`.

**This profile's split.** The receiving MTA checks **address only** and emits
`result=unknown; integrity=delegated; address=…`. `integrity=delegated` means "the MTA did not check
message integrity — the recipient must"; it MUST NOT be read as a pass. Only the recipient SDK computes
`Content-v1` (one implementation, in `did-sdk`), and only it can emit `integrity=pass|fail`.

Rationale: rejecting on integrity at the MTA cannot be attributed (a tampering relay would otherwise be
able to get any legitimate message refused), and recomputing `Content-v1` including attachment digests per
message buys nothing the recipient does not recompute anyway. An MTA MAY additionally verify integrity as
an opt-in per-domain enhancement.

The receiving MTA strips any pre-existing `DID-Auth-Results` at ingress; only its own verdict is trusted.
One header instance per `From` address.

## 7. Anchors

### 7.1 `EmailBinding`

```text
payload_hash = "blake2b:" + BLAKE2b-256( "EmailBinding-v1\n{did}\n{email}\n{issuer_did}\n" )
```

* four lines, every one terminated by `\n` including the last;
* any field containing `\n` or `\r` MUST be rejected (preimage-collision guard);
* `{email}` is trimmed and lowercased; `{issuer_did}` is the literal `AnchorRecord.issuer_did`;
* the receiver rebuilds this from `did` (header), `email` (`From`) and `issuer_did` (anchor record) —
  it never needs the VC.

`issuer_id` in the upstream spec means **`AnchorRecord.issuer_did`** ("trust-chain root"): it does not
change when submission is delegated, so a re-submitted anchor still hashes identically.
Verification order is therefore: fetch anchor → read `issuer_did` → rebuild → compare.

### 7.2 `DomainControl`

```text
payload_hash = "blake2b:" + BLAKE2b-256( "DomainControl-v1\n{domain}\n{issuer_did}\n" )
```

`{domain}` is the ASCII domain, trimmed and lowercased. Bootstrap order (cannot be reversed):

```text
1. issuer creates the DomainControl anchor            -> anchor_id
2. domain owner publishes:
     _email-verification.<domain>. IN TXT "ev-anchor=chain:<anchor_id>"
3. issuer re-checks TXT + anchor before every EmailBinding create/renew
```

### 7.3 Out of scope

* `IssuedVc` — not anchored by this profile. Anchoring a VC commits to its full JSON, which a receiver
  without the VC can never rebuild. Enable it only when selective disclosure is needed.
* `AnchorType` is a caller-supplied label; the chain layer never validates that the label matches the
  preimage actually used. Writers MUST therefore be the single owner of each type they use.

## 8. End-to-end payload (`payload.did`)

Attached to inbound records that carry `DID-Signature`, so the receiving SDK can re-verify on its own:

```json
{
  "signature": "v=1; did=\"did:key:z6Mk…\"; …",
  "body_signed": "the exact record.body that was signed",
  "rcpt_to_raw": "Bob <bob@x.com>, carol@y.com",
  "rcpt_cc_raw": "",
  "attachments": [{ "id": "att_1", "filename": "q3.pdf" }],
  "gateway_time": 1765144656,
  "results": "result=verified; integrity=pass; address=verified; did-id=\"…\""
}
```

Rules:

* **No hashes.** The receiving SDK downloads attachment bytes itself and computes `name_hash`/`file_hash`;
  any digest supplied by the provider would let the provider grade its own homework.
* `body_signed` is the untouched stored body, not the LLM-facing preprocessed one.
* `gateway_time` lets the SDK check the timestamp window without trusting the local clock.
* `body_signed` over 1 MiB ⇒ the record is `not_verifiable`.

## 9. Recipient-side verdict (SDK)

The verdict is keyed on `integrity` + `reason`, **never on `result` alone** (`did_absent` also yields
`result=failed`).

| Condition | Verdict | Action |
|---|---|---|
| no `DID-Signature` | `did_absent` | accept |
| MTA emitted `integrity=delegated` (this profile's normal case) | — | compute integrity locally; never treat as pass |
| `did` not `did:key` / malformed | `did_unsupported` | accept + warn |
| own signature check fails | `signature_invalid` / `body_hash_mismatch` / `rcpt_hash_mismatch` / `timestamp_out_of_window` | **reject** |
| anchor infrastructure unavailable | `chain_unavailable` | accept + flag |
| anchor check fails | `anchor_not_found` / `anchor_type_mismatch` / `anchor_hash_mismatch` / `anchor_revoked` / `anchor_expired` | **reject** |
| attachment bytes unfetchable | `attachment_fetch_failed` | accept + flag |
| payload missing `body_signed` | `not_verifiable` | accept + flag |
| everything passes | `verified` | accept |

`reject` means: not delivered to the LLM, not written to the normal inbound index; an audit copy is
written and an event logged. Under `policy=record` nothing is rejected — the verdict is only logged.

**`not_verifiable` never equals `verified`.** Missing inputs are reported as missing, not as passing.

## 10. Error / reason codes

`did_absent`, `did_unsupported`, `signature_invalid`, `body_hash_mismatch`, `rcpt_hash_mismatch`,
`timestamp_out_of_window`, `anchor_not_found`, `anchor_type_mismatch`, `anchor_hash_mismatch`,
`anchor_revoked`, `anchor_expired`, `chain_unavailable`, `attachment_fetch_failed`, `not_verifiable`.

Client-facing send errors: `did_unavailable` (the `did` extra is not installed),
`did_rcpt_filtered` (a submitted recipient would be dropped by whitelist/board filtering),
`domain_control_required` (no valid `DomainControl` for the sender's domain).

The full list is also mirrored into the vector file under `constants.errors` so every language pins the
same strings.

## 11. Vectors

`protocol/vectors/did-signature.json` is the single source of truth for byte layouts. Groups:
`constants`, `content_v1`, `rcpt_hash`, `signing_input`, `header`, `payload_hash`, `auth_results`,
`verdict`, `payload`.

Regenerate with:

```bash
python3 protocol/vectors/gen_did_vectors.py
```

The generator fixes the key seed, so output is deterministic. It also asserts that the header's `bh`/`rh`
come from the same vector cases (a header echo must never be recomputed independently).

Mirroring: the `aimail` repo keeps a byte-identical copy at `contract/did-signature-vectors.json`;
CI compares the two.

## 12. Change control

1. This file is normative for the wire format; the plan document only explains intent.
2. Byte-layout changes require: update here → regenerate vectors → update all three implementations
   (did-sdk / gateway / SDK glue) → bump `v` if incompatible.
3. `did-sdk` v0.3.0 owns the mail-layer implementation (`Content-v1`, header codec, Ed25519) so that Rust,
   Python and TypeScript cannot drift. The gateway's `crates/mail-anchor` owns the anchor layer only and
   MUST NOT re-implement the mail layer.
